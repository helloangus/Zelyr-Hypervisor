# P8-W03 Fixture Reproducibility and Shutdown/Isolation Evidence Requirements

**Status:** Proposed detailed design; implementation not claimed.  
**Parent:** [P8-W03 detailed design](README.md).

## 1. Purpose

This file fixes the two requirement sets the plan assigns to W03 that do not
belong in the fact catalog itself: what makes the boot contract *testable*
(fixture reproducibility, P8-V20 dependency) and what the contract must
require for *artifact isolation and shutdown evidence* (plan work-sequence
items 3–4). W03 states requirements here; the fixture artifact is owned by
[P8-W15](../p8-w15-reproducible-linux-fixture/README.md) and the automated
matrix by [P8-W16](../p8-w16-automated-linux-regression/README.md).

## 2. Artifact ownership versus Guest isolation requirements

The boot contract's isolation requirements (checked at W03-DV04) are:

1. **Backing provenance.** Every boot artifact is backed exclusively by
   allocatable Host memory owned by the target VM, per the P2 allocation and
   P4 Guest-memory ownership contracts (assumed; failure boundary: if P4
   delivers a different ownership model, the boot lifetime facts B7-2/B7-3
   must be re-reviewed before any implementation relies on them). No boot
   path may map or copy from Host image, Host DTB, hypervisor, or reserved
   Host ranges.
2. **No host-fact disclosure.** No boot artifact's *content* may disclose a
   host physical address, host IRQ, board/SoC identity, or host firmware
   property; content authority is the Guest DTB contract
   ([P8-W04](../p8-w04-guest-dtb-contract/README.md)) and the pinned Linux
   artifacts, but the boot contract owns the prohibition for Image,
   initramfs, and placement metadata.
3. **Bounded acceptance.** The boot input rules (B1-4) are part of the
   isolation boundary: oversize, misaligned, or overlapping artifact inputs
   are rejected before Guest entry with a structured boot-input rejection;
   no code path may pass unvalidated artifact geometry to Stage-2 mapping.
   This requirement binds the future loader implementation (W09/W12) without
   designing it.
4. **Lifecycle closure.** Artifact regions have exactly one owner (the VM)
   from placement to destruction (B7-2); the shutdown facts (B8-3) must make
   release observable so the isolation claim is testable, not assumed.

## 3. Fixture reproducibility requirements (P8-V20 boundary)

The boot contract is testable only against a reproducible fixture. The
contract's testability section must require that the following categories are
either version-pinned in the repository or generated by a pinned, deterministic
procedure — the choice and the artifact are W15's:

| Fixture category | Requirement stated by W03 | Owner |
|---|---|---|
| Linux kernel source revision | pinned exactly (commit/tag); the pinned revision must document the boot protocol revision the contract binds to | [P8-W15](../p8-w15-reproducible-linux-fixture/README.md) |
| Kernel configuration | pinned as a versioned artifact; must not be derived from a host system | W15 |
| Built Image | either a versioned binary artifact or reproducibly built by a pinned procedure from the pinned source/config | W15 |
| Initramfs content | pinned content or pinned build recipe; must reach an interactive userspace shell for P8-V13 | W15 |
| Bootargs | pinned string, delivered via the DTB `/chosen` path per B1-3 | W15 (values); W03 owns the delivery fact |
| Machine-side parameters | vCPU count, RAM size, and any VM configuration used by boot tests come from the machine/boot contract categories with routed values — never invented by the fixture | W15 consumes; W02 routes |

Additional requirements the contract must state:

- **Determinism statement.** Same fixture inputs + same machine identity ⇒
  same boot-visible entry state and same boot-progress markers, except for
  documented non-determinism (architected counter values, timing-dependent
  log interleaving). Any other divergence is a defect to record, not noise to
  tolerate.
- **Marker discipline.** Boot-progress evidence is defined by Guest-visible
  markers (earlycon output, kernel log milestones, userspace shell prompt),
  named in the contract's testability section; `start_kernel` alone is
  insufficient per P8-V13. The contract names the marker *categories*;
  concrete marker strings are fixture facts owned by W15.
- **Fixture–contract drift rule.** If the fixture must move (new kernel
  revision, new initramfs), the change is reviewed against the contract's
  external-standard bindings and compatibility section; a fixture change that
  moves a Guest-visible boot fact is a contract change, not a fixture edit.

## 4. Shutdown evidence requirements (P8-V04 boundary)

The contract's testability section must state what shutdown evidence a boot
test must produce:

1. **Initiation marker.** The Guest's shutdown request is observable
   (Guest-side action via the PSCI path; the observable is the resulting
   behavior, not the conduit encoding — values routed to W06).
2. **Terminal-state observation.** The VM reaches the terminal lifecycle
   state of B8-2, observable in hypervisor diagnostics/telemetry (per the
   P0 diagnostics and P6/P7 telemetry assumed contracts), with no further
   Guest execution.
3. **Resource-visibility observation.** The release claim of B8-3 is
   observable (no Guest-owned memory remains live/mapped; VMID and vCPU
   state reclaimed per the P4 contracts) at the evidence level the P4/P7
   records define.
4. **Repeat behavior.** Repeated boot→shutdown cycles produce the same
   observations (P8-V22 dependency); no stale-state divergence is tolerated
   as "known behavior".
5. **Failure path.** A shutdown that cannot complete (e.g., vCPU in an
   unexpected state) produces a structured diagnostic and a defined fallback
   terminal state per the established failure-classification contracts —
   never a hang presented as shutdown, and never a hypervisor panic. (Linux
   is a guest: a Guest-side shutdown anomaly is a VM-facing error.)

## 5. Non-responsibilities

This file does not select the fixture, name the Linux revision, define marker
strings, design the shutdown mechanism, or specify the automated harness.
Those are W15/W06/W16 scope respectively. Where a requirement here appears to
force such a choice, the choice is routed per the W02 governance and the
requirement is restated as a route.
