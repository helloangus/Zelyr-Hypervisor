## 1. ADR 状态与规范性

| 状态 | 含义 | 规范性 |
|---|---|---|
| Proposed（提议） | 评审中的开放架构提案 | 不约束行为；作者可自由修改 |
| Accepted（已接受） | 项目遵循的决策 | 规范性；约束设计、代码和评审 |
| Rejected（已否决） | 有理由地考虑并拒绝的提案 | 不约束行为，但作为先例有约束力；重新讨论须提出引用新信息的 Proposed ADR |
| Deferred（已延期） | 承认真实需求但推迟，且记录重新评估触发条件 | 不约束行为；触发条件说明何时重启 |
| Superseded（已替代） | 被具名后继替代；历史正文不变 | 不再约束行为；后继文档约束行为 |

状态转换：

- **Proposed → Accepted 或 Rejected：** 按 ADR 所记录的评审作出决策；记录决策、日期、评审者／所有者身份及承载 PR，见[集成流程](../development/integration-workflow.md)。
- **Accepted → Superseded：** 只有后续 ADR 在其 Supersedes 字段具名本 ADR 才可转换；被替代文件的状态行添加后继指针，其他内容不改。
- **Accepted → Deferred 不是转换：** 延期项从未被接受。若已接受决策须暂停执行，应记录为缺陷，而不是改写状态。
- **Deferred → Proposed 或 Rejected：** 当重新评估触发条件成立，或所有者关闭问题时转换。
- **撤回：** 评审前，在 Proposed 文件的变更历史记录（若从未合并可直接删除文件）；已合并的 Proposed 状态撤回时，沿用 Rejected 路径。

## 2. 何时需要 ADR

以下变更**必须**有 ADR：

1. 与[ADR 基线](adr-000-architecture-baseline-v0.1.md)中已接受的决策或实施不变量冲突、覆盖或缩窄其含义；少数例外遵循基线的架构变更规则。
2. 对登记表中标为“待定”的条目（ADR-054 至 ADR-058 及基线第 18 节开放问题）作出具有架构影响的决定。
3. 越过其他基线规定的 ADR 门槛；通过引用而非重述识别，例如[工具链基线](../development/toolchain-baseline.md)中对 TCB 有关键作用的不稳定特性、通道／固定机制变更，[构建目标基线](../development/build-target-baseline.md)及[构建选择治理](../development/build-profile-governance.md)的门槛。
4. 引入无法从基线推导的新架构原则、分层边界、对象模型元素或安全／信任边界决策。
5. 改变架构变更流程本身，即本文规则。

以下属于已批准详细设计及冻结契约内部的局部实施选择，**不需要 ADR**：
在既定边界内的普通模块／函数设计、例行版本升级、遵循相应治理的目标或依赖增加、
按[文档基线](../development/documentation-baseline.zh-CN.md)进行的文档维护，
以及由编码指南负责的代码级决策。

**疑问处理：** 不确定时，标记为 `ADR Required` 并交由所有者决定。多一份不必要的 ADR
成本是一份文档；漏掉必需 ADR 的成本是架构。

## 3. 标签含义

- **`ADR Required`：** 当工作被*阻塞*时记录：必需选择与已接受决策冲突、落入第 2.1–2.5 节，
  或越过引用的门槛。在工作跟踪位置（实施记录、PR 或 issue）记录阻塞问题并引用受影响决策 ID；
  受影响工作停止，直到 ADR 路径完成。
- **`Architecture Change Request`：** 贡献者*提议*改变已接受架构时记录，
  不论当前是否有工作被阻塞。

两种标签都产生同一种交付物——Proposed ADR 及其评审，不能分叉成两套流程。

## 4. 冲突、替代与评审流程

```text
发现冲突（或提出变更）
  -> 在受影响工作跟踪位置记录标签及所引用的决策 ID；若被阻塞则停止该部分工作
  -> 用 docs/templates/adr-template.md 起草 Proposed ADR
       - 编号：已登记最高 ID 之后的下一个未使用编号
       - Supersedes：适用时列明被替代决策
       - 背景须引用受影响的已接受正文
  -> 评审：在 ADR 变更历史中记录决策、理由、评审者／所有者及承载 PR；只按集成流程合并
  -> 接受时：更新索引行（第 6 节）和每份被替代文件的状态行（该文件唯一可改处）
  -> 否决时：写明理由；该记录保留为先例
```

历史保留规则：

- 已接受和已替代 ADR 的正文永不重写。接受后仅允许改动：（a）状态／替代关系头信息行；
  （b）仅对 adr-000 内部登记表，在状态行添加指向作出决策的独立 ADR 的指针，不能改决策正文。
  其他一切修改，包括勘误，都须通过替代或修订 ADR。
- 基线 ADR 若被替代，应由后继基线 ADR 整体替代，不能通过分散修改替代。

## 5. 与登记表的关系（资料性）

adr-000 内部登记表的状态词由原文定义，本文不重新定义（大致对应：“已确定”≈Accepted，
“长期预留”≈长期保留的意向，“待定”≈待决，“否决”≈Rejected）。在操作上，
“待定”项由第 4 节路径中的独立 ADR 决定；其登记表行随后只按第 4 节的狭义编辑规则添加指针。
不得直接编辑登记表行来决定、重述或“清理”条目。

## 附录：示例（资料性）

**以下示例纯属假设，不解决任何问题，也不创建 ADR。**

- *假设提议：* 为缩短某个中断路径，允许 Hypervisor Core 按板卡名称分支。
- *冲突：* 直接违背已接受的板卡无关性决策（登记表 ADR-052、ADR-043：Core 不能按板卡名称驱动逻辑）和 Core 不变量。
- *决策测试（第 2 节）：* 属于第 2.1 节，需有 ADR。
- *标签：* 若只是提议、工作尚未阻塞，使用 `Architecture Change Request`；
  若某个 P1 任务必须依赖该变更，停止任务并标记 `ADR Required`。
- *正确路径（第 4 节）：* 起草具有下一个未使用编号的 Proposed ADR，具名替代 ADR-052／ADR-043，
  说明性能理由、备选方案（平台能力查询、BSP／Quirk 位置）及引用已接受正文的背景；
  送交评审；接受后更新索引行与两处被替代状态行，不能改其他正文。在接受前，Core 仍不得按板卡名称分支。
- *要点：* 评审者采用第 2 节的决策测试，变更采用第 4 节的路径。
