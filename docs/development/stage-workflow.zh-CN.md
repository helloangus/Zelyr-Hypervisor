## 1. 分层模型

七个层级把每个阶段从架构带到完成。位置引用文档基线中的类别清单和阶段分离规则；
本文不重复列举目录规则。

| 层级 | 制品与位置（引用） | 输入（本层工作前必须具备） | 输出 |
|---|---|---|---|
| L1 — 架构决策（ADR） | ADR 类别中的 `docs/adr/` 文档和索引 | 已记录的冲突、有意的架构提案或待决问题；ADR 生命周期规则 | 已接受／否决／延期／替代的决策；升级处理记录 |
| L2 — 阶段任务书 | `docs/stages/<id>/task-book-v*.md` | ADR 基线；阶段任务 | 必需成果、约束、验证矩阵、退出条件；有界工作包图 |
| L3 — 工作包计划 | `docs/stages/<id>/plans/` 及计划索引 | 任务书、ADR、计划索引中的前置契约 | 目标、范围分类、有界工作顺序、验收、移交、前置／消费者链接 |
| L4 — 详细设计 | `docs/stages/<id>/implementation/<slug>/` 入口及支持文件 | 计划；涉及代码时的编码指南；经路由的详细参考 | 实施级契约、步骤、验证矩阵、移交；对治理工作包则为计划所留待设计的制品契约 |
| L5 — 实施记录 | `docs/stages/<id>/implementation/<slug>-record.md` | 正在实施的设计 | 实际采用的决策、变更制品、偏差；指向设计、计划及验证记录的链接 |
| L6 — 验证记录 | `docs/stages/<id>/verification/<slug>-verification.md` | 设计的验证矩阵；实际执行／评审 | 各 ID 的已运行／失败／阻塞／未运行证据，以及证明／不证明什么；完成声明的唯一位置 |
| L7 — 阶段完成评审及报告 | 阶段验证区；移交材料内容 | 每个工作包的 L5／L6 记录；任务书退出条件 | 阶段完成声明；汇总的移交材料 |

## 2. 各层字段

每层条目都有以下六个字段。

### L1 — 架构决策

- **回答的问题：** 适用何种架构，以及架构如何变化。
- **决策权威：** 架构及其变更流程（见 ADR 流程）。
- **升级边界：** 不代替设计或实施；不得暗中修改已接受决策（标签遵循 ADR 流程）。
- **准入：** 第 3 节准入表中的“架构提案”。
- **消费者：** 所有层，尤其是 L2 任务书和 L4 设计。
- **失败行为：** 缺失或冲突的决策在 ADR 路径完成前阻塞下游；不得临时绕过。

### L2 — 阶段任务书

- **回答的问题：** 本阶段必须实现什么。
- **决策权威：** ADR 范围内的阶段成果及验证 ID。
- **升级边界：** 不得包含函数、模块或文件级实施细节。
- **准入：** 第 3 节准入表中的“编写／修改任务书或计划”。
- **消费者：** L3 计划及 L7 完成评审。
- **失败行为：** 任务书缺陷按规划指南的变更路径在同一次变更中修正；agent 不自行重新解释成果。

### L3 — 工作包计划

- **回答的问题：** 如何将一个成果限定为工作、顺序与验收条件。
- **决策权威：** 任务书范围内的工作包边界、顺序和验收措辞。
- **升级边界：** 不得规定命令、crate 结构或签名。
- **准入：** 第 3 节准入表中的“编写／修改任务书或计划”。
- **消费者：** L4 设计及选择工作包的每位 agent。
- **失败行为：** 计划把决策留给不存在的设计时，实施应被阻塞并记录，而非允许边编码边设计。

### L4 — 详细设计

- **回答的问题：** 如何实施、验证该工作包。
- **决策权威：** 计划划为阶段内部设计自由度的事项。
- **升级边界：** 不得解决与已接受决策的冲突（按 ADR 流程使用标签），也不得声称完成。
- **准入：** 第 3 节准入表中的“涉及代码的变更”和“治理／政策变更”。
- **消费者：** L5／L6 和实施 agent。
- **失败行为：** 设计缺口或矛盾须记录为所属工作包的阻塞；交付前设计状态保持“proposed”。

### L5 — 实施记录

- **回答的问题：** 实际做了什么、作出哪些决定。
- **决策权威：** 无；它记录事实，不制定新规则。
- **升级边界：** 不得发明政策来为偏差辩解；偏差须陈述并有所有者，不得暗中吸收。
- **准入：** 第 3 节中与该变更对应的行。
- **消费者：** L6、L7、评审者。
- **失败行为：** 变更缺少记录即评审失败；命令日志与完成声明不属于此处。

### L6 — 验证记录

- **回答的问题：** 有何证据、证明什么。
- **决策权威：** 无；它报告证据，不重新解释验收。
- **升级边界：** 不得把“阻塞”或“未运行”升级成“已通过”；完成声明只在此处。
- **准入：** 设计的验证矩阵，实际执行或评审。
- **消费者：** L7、阶段消费者、未来审计者。
- **失败行为：** 证据缺口应如实说明，不得用流程文字豁免。

### L7 — 阶段完成评审及报告

- **回答的问题：** 阶段是否完成，下阶段收到什么。
- **决策权威：** 仅凭 L6 证据及 L2 退出条件作出完成声明。
- **升级边界：** 退出条件缺少证据的阶段不得通过。
- **准入：** 每个工作包的 L5／L6 记录齐全且真实。
- **消费者：** 下阶段规划及 P1 类移交材料。
- **失败行为：** 缺少证据就不能完成；在有证据前阶段保持开放。

## 3. 准入决策表

“已具备”指具名制品位于权威位置，其状态允许该活动，且执行者已按文档索引路由规则阅读。

| 活动 | 开始前须具备 | 阻塞时的升级处理 |
|---|---|---|
| 工作包内涉及代码的变更 | 已批准计划；针对该变更的已批准详细设计；完成编码指南事前检查；计划索引的前置契约已交付，或其缺失已记录为阻塞 | 计划把必需决策推迟给“所属设计”，但该位置没有设计时，必须记录阻塞，不能边编码边设计 |
| P0 类工作包内的治理／政策变更（文档、契约、配置） | 已批准计划；承载计划所留待决策的设计级制品契约（已确立的 P0 模式），或计划明确说明其本身就是契约 | 规范性规则没有主管文档时，应按文档基线门槛作为政策决策处理，不可局部编辑 |
| 编写／修改任务书或计划 | Plan Agent 指南；ADR 基线；适用任务书；阶段工作包规划 skill | 任务书和计划不能从实施说明反向编写；内容沿层级单向向下，冲突沿层级向上升级 |
| 架构提案或变更已接受决策 | 按 ADR 生命周期与模板起草的 ADR | 不能作为其他工作包的副作用执行；替代 ADR 是独立的经评审变更 |
| 工作中发现与已接受决策或声明门槛的冲突 | 根据 ADR 流程定义，标记 `ADR Required`（工作受阻）或 `Architecture Change Request`（有意提案），并记录 | 受影响工作止于边界；不能局部重新设计或暗中重释 |
| 合并与集成 | 集成流程政策；CI 基线中配置的必需检查 | 低于 L7 的层级不能授予阶段完成；受政策约束的绕过须记录，不能作为日常手段 |
| 阶段完成声明 | 各工作包按任务书验证矩阵提供证据；退出条件经过评审 | 缺少证据即完成失败，流程文字不能豁免；这正是本工作包要防止的情况 |

推论：

- **计划本身不授权编码。** 计划索引的阅读顺序（“编码变更须有编码指南和已批准的详细设计”）
  及任务书交付层级规则，是上表第一行的依据。
- **流程文字不代替设计。** 为了在没有设计时开始编码而添加流程说明，是评审失败，不是捷径。

## 4. 可追溯性与证据位置规则

`P<stage>-Wxx` 工作包 ID 和 `P<stage>-Vxx` 验证 ID 是可追溯键。

1. **设计 ↔ 计划：** 每份详细设计的头信息须具名其上级计划；设计映射的每项需求应沿用其落实的计划措辞。
   对涉及代码与治理的设计，都必须使用既有 P0 模式中的“需求 → 设计位置 → 验收”表。
2. **实施记录 ↔ 设计 ↔ 计划：** 实施记录须具名实施的设计目录、满足的计划、变更制品、
   实际决策及偏差，并链接验证记录。不得包含命令日志或完成声明。
3. **验证记录 ↔ 验证矩阵：** 验证记录中的每项对应设计验证矩阵 ID 及任务书的 `P<stage>-Vxx` ID；
   记录命令、环境、时间戳、原因和已运行／失败／阻塞／未运行状态，并逐项说明证明／不证明什么。
   完成声明只在此处。
4. **同次变更规则：** 在同一次变更中更新被该变更否定的文档（引用文档基线的要求）；
   契约落后于实施是缺陷，不是 TODO。
5. **位置规则：** 决策放在实施记录，证据放在验证记录；两者均不能转移到设计、任务书、计划或流程文件中。
   此规则引用文档基线的阶段分离，不另行制定。
6. **移交规则：** 阶段移交材料（L7 输出）通过链接各层成果——记录、证据、主管契约——组装，
   不能复制其正文；阶段依赖图（P0-W22）把该规则应用于 P0 材料。
7. **失败归属规则：** 每项阻塞或失败活动都具名所属层级和工作包，使 agent 不会面临无人负责的失败。
   这是贡献者流程中按阶段处理模式的推广。

## 5. 禁止混写规则

- 流程文档（本文、指南、政策）不能代替已批准的详细设计；任务书不能包含函数或模块实施细节。
  每条都以第 2 节层级字段作为可检查的执行界面。
- 每份制品的内容留在文档基线定义的类别内；两层都需要的规则只在主管层写一次，另一层以链接引用。
- 文档不能通过自创层级、位置或隐含类别建立新规则；新类别应遵循文档基线门槛。
- 各层状态须真实：设计标为“proposed”；只有 L6 可以说“passed”；只有 L7 可以说阶段已完成。
