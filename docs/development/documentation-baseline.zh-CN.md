## 1. 类别清单

仓库中每份文档恰好属于下列一个类别。状态决定评审权威性：规范性类别中的文档约束工作；
资料性文档用于说明。“有条件”表示批准且经路由纳入时为规范性，否则为资料性。

| 类别 | 位置 | 状态 | 权威职责 |
|---|---|---|---|
| 根目录导航 | 根目录 `README.md`、`AGENTS.md` | 规范性 | 必读入口及路由 |
| 文档治理 | `docs/README.md`、`docs/development/documentation-baseline.md` | 规范性 | 路由、优先级、分类和元数据规则 |
| 架构决策（ADR） | `docs/adr/` | 规范性 | 已接受的架构决策及其变更流程；生命周期细节由 ADR 治理文档负责 |
| 架构说明 | `docs/architecture/` | 有条件 | 批准后的跨领域架构说明 |
| ABI／线格式契约 | `docs/abi/` | 存在时为规范性 | 版本化外部契约；P0 阶段没有 |
| 机型契约 | `docs/machine-types/` | 存在时为规范性 | 版本化 Guest 机型；P0 阶段没有 |
| 平台契约 | `docs/platform/` | 有条件 | PlatformInfo／支持等级／BSP／quirk 契约 |
| 测试 | `docs/testing/` | 有条件 | 批准后的测试策略、环境和证据规则 |
| 安全 | `docs/security/` | 有条件 | 威胁模型、安全与 unsafe 审计记录 |
| 开发指南 | `docs/development/` | 规范性 | 必读的简明 agent 指南、路由的详细参考及各主题治理基线 |
| 模板 | `docs/templates/` | 规则为规范性，内容为资料性 | 重复文档类型须先有批准模板，模板正文供使用 |
| 阶段文档 | `docs/stages/<id>/` | 规范性 | 任务书（做什么）、计划（有界工作包）、实施（设计和记录）、验证（证据），见第 5 节 |
| 实施记录 | `docs/stages/<id>/implementation/<slug>-record.md` | 阶段内部事实记录 | 记录决策、变更制品和偏差；不存证据日志 |
| 验证记录 | `docs/stages/<id>/verification/<slug>-verification.md` | 阶段内部事实记录 | 记录证据、执行／未执行状态；完成声明只放在此处 |

清单规则：

- 增减类别只能遵循第 4 节门槛；不能通过自创位置暗中增加类别。
- 规范性文档中的资料性内容应在使用处标明。

## 2. 规范性／资料性区分

不约束工作的陈述应就地标明其性质。规范性文档的资料性章节须作标记；
资料性文档不得针对项目行为使用“必须”“只能”“禁止”等规范性措辞。
混写而未标注属于一致性缺陷，不只是风格问题。

## 3. 文档元数据规则

每份规范性文档（资料性文档也建议遵守）的开头应包含：

- **状态**：生命周期位置，例如契约的 proposed／accepted／superseded。
- **范围**：规定内容以及明确不规定的内容。
- **版本**：`v<major>.<minor>`。若增加或细化规范性内容且原指导仍有效，则增加次版本；
  若重写使原指导失效，则增加主版本。
- **所有者／变更背景**：所属工作包或角色，以及可变更的原因。
- **替代**：被替代的文档，或无。

替代机制：被替代文档不得暗中改写或删除；后继文档须在“替代”字段指明它，
前件状态更新为 superseded 并指向后继。ADR 的专门生命周期规则由 `docs/adr/` 中的治理文档负责，
本文只作指向。

同次变更规则：代码变更若使某文档不再正确，须在同一次变更中更新文档。
评审发现契约落后于实现时，应视为缺陷，而不是 TODO。

## 4. 版本与变更门槛

- **例行维护**（普通 PR 评审）：类别内增加内容、修正元数据、修复断链、澄清资料性内容。
- **须有政策决策**（变更前记录问题并由所有者决策）：增加、删除或迁移类别；
  重新分类目录状态；迁移已接受契约（执行时还须取得所属工作包同意）。
- **须有 ADR**：改变已接受的架构决策或 ADR 变更流程，转交[`docs/adr/README.md`](../adr/README.md)。

## 5. 阶段文档分离

每个阶段的 `docs/stages/<id>/` 中恰好如下分层：

| 位置 | 可包含 | 不可包含 |
|---|---|---|
| `task-book-v*.md` | 必需成果、约束、验证矩阵、退出条件 | 详细设计、函数／模块规格、实施说明、证据 |
| `plans/` | 有界工作包计划及索引 | 未获批准却声称已批准的设计、实施说明、证据 |
| `implementation/` | 详细设计与实施记录 | 验证证据、完成声明、应归属阶段外规范性类别的政策 |
| `verification/` | 各工作包证据与完成报告 | 设计、决策记录、政策 |

理由：计划给出工作粒度，不是实施处方；设计授权实施；记录保持可追溯；验证提供证明。
这些层级之间的职责流转与准入标准由 P0-W21 阶段流程设计负责；本文只规定位置和内容。

## 6. 入口、链接与可引用性

- `docs/` 下每个目录都有 README，说明目录职责及其在第 1 节中的状态类别。
- 所有入口文档中的 Markdown 链接都须在全新 checkout 中可解析。
- 引用其他文档的规范性陈述时，应链接到原文而非重述，以保持单一归属。
- 可引用性：每项 P0 工作包或 P1 规划者的输出，在工作包开始前就应由第 1 节清单确定归属位置。

## 7. 语言版本与翻译权威性

英文源文档以英文版为权威。已接受的 [ADR-000](../adr/adr-000-architecture-baseline-v0.1.md)
是例外：其现有中文正文根据 ADR 历史规则继续具有权威性。ADR-000 英译本只是阅读辅助，
不修订、替代或废止该决策。任何译文都不会独立形成契约、批准、实施声明或验证声明。
出现分歧时以权威原文为准，并通过评审后的变更修正译文。

译文与原文同目录；中文版使用 `.zh-CN.md`，ADR-000 英译本使用 `.en.md`。
保留原文文件名主体和阶段子目录。每份译文开头须有自己的翻译状态、原文相对链接、
翻译所依据的原文 Git blob ID，以及权威性声明。尽管第 2 节规定资料性文档不得独立使用规范性措辞，
译文仍可忠实翻译原文的规范性措辞，但这些措辞不具有独立权威性。
不得暗中删节原文，或在翻译中更改标识符、命令、证据值、日期、批准状态与否定性声明。
链接应优先指向已有且当前有效的译文，否则指向权威原文。已接受 ADR 的翻译不构成修改原文、
增加反向链接的许可；应通过 ADR 索引关联。

英文原文已有中文版时，若原文属于 ADR、治理文件、阶段任务书、已批准详细设计或完成报告，
则变更须在同一 PR 中同步译文。其他已有译文可暂时滞后，但须醒目标记 `Outdated`，
并保留所依据的原文 blob ID。尚未翻译的原文仍在分阶段翻译清单中；缺少译文不表示译文已更新。
[文档检查](quality-gates.md)校验配对元数据和同步规则。译文状态不改变原文的状态或版本。
