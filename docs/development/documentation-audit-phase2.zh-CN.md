## 2. 方法与证据边界

每份文档均完整阅读，没有依赖被截断的批量输出。审阅者记录文件路径与 Git blob、完整行范围、标题/章节、审阅日期、治理权威来源、问题或引用、反证和审阅说明。默认阅读英文源文件；译文结合其源文档和语言版本规则审阅。除非文档自身的当前权威与证据另有说明，工作包设计一律视为 Proposed。

详细记录见 [JSON Lines 台账](documentation-audit-phase2-reviews.jsonl)和 [CSV 视图](documentation-audit-phase2-reviews.csv)。JSON Lines 保留每条发现及其证据/反证对象；CSV 便于排序和筛选。重复的跨文档引用保留为引用，不重复计作独立缺陷。对 Proposed 设计的发现属于设计或验收阻塞项，不是已观测到的运行时漏洞。

审阅过程中按文档主张，定向对照了治理任务书、计划、ADR、当前基线修订、实现记录、验证记录，以及部分代码/CI。P8 TVAL 合同问题还对照了[Arm AArch64 Generic Timer Programmer’s Guide](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Generic%20Timer.pdf?revision=c710e7a7-9f52-4901-8c9d-91b19f44f9c7)。

本次审计没有运行 Rust 测试、QEMU、硬件或完整运行时测试套件。全文覆盖并不等于包间边完整：第 3 项仍需为 125 个包映射输入、输出、验收证据、归属、生命周期、失败/回滚及验证消费者。剩余队列也包括重点交接检查和更广泛的机械验证。此次审阅没有修复或批准设计、ADR、代码或发现项。

## 5. 修复路线

这些发现建议后续工作按以下顺序复核；它们不授权直接修复：

1. 先解决规范权威归属和准入权威：AUD-006/007、AUTH-01 审批出处、已批准的 P8 机器合同路线，以及各阶段要求的上游证据。
2. 再协调生产者合同后才实现消费者：P1 映射覆盖；P2/P3 地址、缓冲区、生命周期与传输合同；P4 多地址空间和 grant 归属；P5 句柄/撤销/分发合同；P6 物理/虚拟中断完成路径；P7 生命周期与同步。
3. 合同稳定后再对齐场景可达性和验收证据：Guest 地址探测、W13 故障分类、P8 回归 oracle，以及 P6/P7 会计单位。
4. 接着执行交接队列第 3 项，完成全部 package map；之后开展优先级边界与实现证据检查。变更应由所属阶段处理。本报告不批准修改已接受的 ADR 或实现 Proposed 设计。
