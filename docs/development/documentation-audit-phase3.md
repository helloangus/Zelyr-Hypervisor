## 2. Dependency and handoff cycle review

The review followed actual plan and detailed-design producer/consumer statements, then checked the owning task-book sequence and whether a stable interface or post-run feedback explains a reverse edge. A package-reference cycle alone does not prove an execution deadlock: many documents describe compatibility constraints in both directions. The significant candidates resolve as follows.

| Candidate edges | Assessment | Admission order or remaining blocker |
|---|---|---|

W03 publishes a draft; W04 plans metadata against it; W03 seals; W04 then initializes. | The interface order is explicit in the W03 runtime-storage contract. W04 remains blocked by W04-LAYOUT and W04-MAP; no allocator readiness is implied. |

## 3. Priority handoff findings

The package mappings reinforce these cross-stage blockers and evidence limits. They are audit findings for owner review, not authorization to change an ADR or implement a proposed design.

| Boundary | Evidence and impact |
|---|---|
| P1 memory mapping → P2/P3/P4 allocation consumers (AUD-003) | P2 W04 allocates physical frames and its W04-MAP gate covers writable access to allocator metadata only. That does not establish writable Host mappings for ordinary allocated frames used as P3 stacks or P4 page tables. P4’s proposed mapping grant also has an unresolved device-page/permission-slice boundary. Assign the producer, attributes, lifetime, revocation and rollback before consumers rely on a physical allocation as a writable pointer. |
| P3 notification accounting → P6/P7/P8 scenarios | P3 W07 permits coalescing/latest-wins delivery, but W12/W13 acceptance language compares send and receive counts as if every send must arrive. Align the units and count accepted delivery separately from coalesced or rejected attempts before those tests can serve as evidence. |
| P6 physical timer interrupt → Guest completion (P6-W03/W06) | W03 describes EOImode=0 combined completion; W06 requires the physical PPI to remain acknowledged but active until the Guest-visible timer event completes, with a later P6-W09 hook. The designs identify split completion as requiring an ACR if W03 cannot express it. No approved ACR, matching producer API or runtime evidence was found; the edge is blocked. |
| P7 wakeup and lifecycle → timer/scheduler consumers (AUD-001) | W06’s blocker can commit `Blocked` after an event is published while the waker still observes `Running` and returns; `wake_pending` is not consumed under a shared synchronization protocol. W08 repeats the gap around idle intent and WFE. This remains a proposed-protocol blocker, not an executed runtime failure. |
| P4 address-space and P5 rights → P7/P8 lifecycle | P4’s single-space activation assumptions do not supply P7’s multi-VM switch semantics (AUD-004). P5’s authorize-then-use path lacks a stable target/grant lifetime across unlock and execution. These require producer-owned reactivation and use/revocation contracts. |
| P8 machine and regression contracts | P8-W01’s dated baseline says P1–P7 implementation/evidence is absent, contrary to the current snapshot; its own workflow requires refreshing the inventory. W13’s fault-classification order may overlap W12’s Stage-2 fault expectations, and the W13 panic-to-P7 Guest-faulted owner is unassigned. P8 scenario and fixture loops need the ordered content interfaces in §2. |
| Completion evidence and artifact identity | P0-W16/W17 policy and entry points exist, but the profile vocabulary required by the hypervisor artifact name is still empty; policy delivery does not prove a concrete artifact can be named. P6-W12/W13 likewise need to carry the P1 NC6 transfer as P6-V29 rather than infer asynchronous-vector execution from older synchronous fixtures. |

Other package-level findings are preserved in each row, including P3 CAS ordering and timeout-slot reuse, P4 re-entry and mapping grants, P5 handle/revocation races, P6 GIC completion and SGI units, P7 lost-wakeup state transitions, and P8 fault, timer and fixture classification. Existing AUD-001–007 and AUTH-01 remain open unless the owning evidence resolves them.

## 4. Repair route and limits

Use the following order for a later, separately authorized repair program: settle authoritative source ownership and machine-value gates; close producer contracts for memory mapping, interrupt completion, lifecycle, notification units, and authorization lifetime; freeze regression-envelope and fixture-content interfaces; then run the owner-specific host, target, and QEMU evidence. Preserve hardware, asynchronous exception, SMP, and whole-stage claims at the exact scope of their source records.

This phase did not modify code, accepted ADRs, package designs, or stage evidence. It did not run Rust tests, QEMU, hardware, or package scenarios. Documentation and translation checks are reported with the phase delivery. Handoff queue items 4–6 remain open, including the full prioritized-boundary re-review, selective source/runtime evidence verification, and remaining mechanical checks. The repository-wide audit is not complete, and no PR was merged.
