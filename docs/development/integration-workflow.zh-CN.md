## 政策

`main` 是唯一集成分支。新开发不得直接在 `main` 进行。每项一致的变更从当前 `main`
新建分支开始，推送到 GitHub；只有承载该变更的 PR 所配置的必需在线检查通过后，
才能经 GitHub PR 合并到 `main`。

本政策之前的 W01 引导提交是历史基线记录，不构成后续开发的例外。

## 必需的变更生命周期

1. 对有界工作包或一致的文档变更创建一个分支。使用描述性命名空间，例如
   `p0/w02-toolchain`、`p1/w01-el2-entry` 或 `docs/topic`。
2. 只实施经批准、属于该分支范围的变更，并在需要时将验证记录写入阶段内的实施和验证位置。
3. 将分支推送到配置的 GitHub 远端，并创建以 `main` 为基础分支的 PR。
   PR 描述应标识工作包或政策变更、变更的契约、已运行与未运行的验证，以及未解决的冲突。
4. 等待该 PR 的所有 GitHub **必需**检查通过。缺失、取消、跳过或失败的必需检查都不能算作通过证据。
5. 必需检查通过后，只有授权维护者才可将 PR 合并至 `main`。所选 GitHub 合并方式必须保留
   合并变更与 PR 之间可审查的关联。

## 边界与强制机制

- 分支名只是组织元数据，不能代替已批准的详细设计、验证证据或工作包范围检查。
- PR 检查只证明 P0-W20 配置的项目；除非明确收集并报告相应证据，它们不证明 QEMU、Guest 或硬件行为。
- P0-W20 负责 GitHub 工作流触发、必需检查分类、分支保护配置，以及 GitHub 确实强制执行本政策的证据。
  在该工作完成前，本文是必需的人工流程，而非技术强制的证明。
- 政策采用后，禁止直接向 `main` 提交或推送开发变更。GitHub 管理员能够绕过保护，
  不等于获准绕过本政策。
